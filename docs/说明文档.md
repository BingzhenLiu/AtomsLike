# AtomsLike 说明文档

> `README.md` 是入口，本文档回答三件事：**怎么做的（思路与关键取舍）**、**做到什么程度（做了什么 / 没做什么）**、**接着做该做什么（扩展与优先级）**。
> 同步时间：2026-09-22。

## 一、实现思路与关键取舍

### 1. 主链路：先出方案，再动手

```text
输入需求 → Planner 出方案 → 用户批准 → Agent 构建 → 实时预览 → 对话修改 → 版本回溯
```

| 阶段 | 接口 | 代理做什么 | 预算是 |
| --- | --- | --- | --- |
| 规划 | `POST /api/plan` | 只调用一次 `propose_plan`，产出目标 / 核心功能 / 本版不做 / 我的假设 / 待确认问题，**不生成任何代码** | 20s |
| 构建 | `POST /api/generate` | 依次调用 `design_app` → `write_app`，服务端校验通过才算完成 | 55s |

**取舍**：首次生成多了一次往返，换来「用户拿到的东西就是他确认过的东西」。

闸门是**无状态**的：服务端不保存会话，浏览器持有已批准方案并在第二阶段回传。代价是重复序列化一次方案（几百 token），收益是刷新、冷启动、多实例部署都天然安全。后续对话修改不再过闸门，以保住快速迭代的手感。

### 2. 单文件 HTML 产物 —— 最大的稳定性来源

生成结果是一个内联 CSS/JS 的完整文档：没有模块导入、没有依赖安装、没有构建步骤。

**取舍**：牺牲多文件工程的扩展性，换掉「在线编译 / import 解析失败」这一整类翻车点。因此界面**不做文件树**，改成 Preview / Code 双视图 —— 与其做一个假的文件树，不如把代码视图做实。

### 3. 预览当作不可信输入

`iframe srcDoc` + sandbox（只开放脚本、表单、模态框）＋注入式 CSP（阻断网络连接、外部资源、嵌套内容）。生成物在成为版本之前要过四类检查：字段、大小、完整 HTML、危险能力（`src/lib/preview/validate-html.ts`、`harden-html.ts`）。

### 4. 持久化与版本快照

项目、消息、版本和当前选择都存在带 schema version 的 localStorage 根对象里；界面只通过 repository 接口访问存储，将来换成云端实现只需替换这一层。每次成功构建写入**不可变快照**，可随时切换回任意历史版本。生成失败时保留上一可用版本，并以稳定错误码 + 一键重试兜底。

### 5. 为什么用 agent，而不是一次补全

一次构建要 3–4 轮模型调用，比单次补全更慢也更贵。换来的东西：

- 可执行的阶段记录 —— 时间线显示真实发生的请求阶段，而不是与请求无关的动画；
- 由校验工具把关的产物 —— 文档不合格时错误会作为工具结果回到模型，模型可以自行修正并重试（`write_app` 最多三次）；
- 不会失控 —— 规划工具一次性保护、构建阶段工具调用总量上限 8 次，超限以稳定的 `OUTPUT_INVALID` 结束，而不是把预算烧到超时。

### 6. Demo Mode：必须的降级路径

没有 key、额度耗尽、网络异常时，应用不带病上阵，而是**明确标注**进入 Demo Mode，用内置模板（记账、番茄钟、习惯打卡）跑完整流程：生成 → 交互 → 修改 → 版本 → 回溯，并始终标 `mode=demo`；不支持的 Prompt 返回 503 `CONFIG_MISSING`，而不是假装成功。Demo 下不显示「重新规划」，因为内置模板无法响应任意反馈。

### 7. Timeline 的诚实原则

时间线由真实请求生命周期驱动，不展示模型隐藏思维，也不声称做过并不存在的四次独立调用。

## 二、完成程度

### 已实现（可演示）

- 首次生成：方案闸门 + 批准后构建，阶段通过 SSE 实时推送；
- 基于当前 HTML 的**对话修改**；
- **版本快照、版本切换、刷新恢复**；
- 生成失败保留上一可用版本 + 稳定错误码 + 一键重试；
- 受限预览、Preview / Code 双视图、Desktop / Tablet / Mobile 预览宽度、窄屏工作流；
- Demo Mode 三个内置示例；
- 容器化交付：多阶段 `Dockerfile` + `docker-compose.yml`（已用 podman 真实构建并运行验证）。

### 已验证

- `npm run lint` / `typecheck` / `test`（10 个文件 35 个用例）/ `next build` 全绿；
- 真实链路端到端（本地 mock OpenAI 兼容端点）：阶段一 `planner:active → completed → plan`，阶段二 `designer → engineer → reviewer → result`，每轮 1 次规划调用 + 3 轮构建调用；
- Demo Mode 走同一套阶段与事件，返回 `mode=demo`；
- 容器：镜像真实构建成功、以非 root（uid 1001）运行、健康检查 `healthy`，demo / live 两种模式都能正常起服务；
- 首页 `force-dynamic`，运行模式在**每次请求**读取环境变量（有测试锁住），容器注入凭据不会被构建期烤死。

### 没做 / 已知限制（主动交代）

1. **线上链接尚未部署** —— 当前最大的缺口，也是硬门槛。
2. **真实模型的端到端验收还没成功**：MiniMax key 认证有效但账户余额不足（402 `insufficient_balance_error`），真实产物尚未生成过；此前所有链路验证走的是本地 mock 端点和 Demo Mode。
3. **没有版本 diff 视图** —— 只有快照切换与回溯，计划里的「并排 diff」未做。
4. **没有导出 / 分享**。
5. **单项目**：一个浏览器工作区只维护一个当前项目。
6. **组件层缺测试**：10 个 `.tsx` 组件零覆盖，其中 `workspace-shell`（SSE 消费 → dispatch → 批准 / 重试 / 取消）最需要补；也没有 E2E。
7. **Demo Mode 只覆盖三个明确示例**，且二次变换重点覆盖记账。
8. 生成应用自身的临时交互状态不会写回宿主项目；持久化的是生成源码与宿主对话 / 版本。
9. 单次构建 55 秒上限（适配 60 秒函数执行预算），超时会保留上一版并可直接重试。

### 与作战计划的差异，以及为什么改

| 计划 | 实际 | 原因 |
| --- | --- | --- |
| 三栏：对话 / 文件树 / 预览 | 对话 + 结果（Preview / Code） | 单文件产物没有文件树，硬做不如把 Code 视图做实 |
| 流式生成多文件代码 | 单文件 HTML | 见「单文件 HTML 产物」一节的取舍 |
| 时间线 + 并排 diff | 版本列表 + 切换 / 回溯 | diff 视图未做，列入下一优先级 |
| 初始化 / **注册** / 主流程 | 新建项目，无账号系统 | 需求原文中「注册」是举例，不投入两小时做账号体系 |

## 三、继续投入的扩展与优先级

1. **部署并拿到公开可访问链接**（Demo Mode 无需 key 即可演示）—— 硬门槛，最高优先。
2. **真实模型验收**：充值或更换 key 后，跑通首次生成 → 二次修改 → 刷新恢复 → 版本回滚 → 失败重试。
3. **版本 diff 视图**：并排对比 + 一键还原。创新分主要靠这块闭环。
4. **补 `workspace-shell` 接线测试**，并做窄屏 / 键盘焦点的人工回归。
5. **演示录屏** 3–5 分钟，降低评审成本。
6. 多项目管理（新建 / 重命名 / 删除 / 切换）。
7. 导出 HTML 与只读分享快照（在保持沙箱边界的前提下）。
8. 把 repository 实现从 localStorage 换成云端存储。

## 附：本地运行与验证

要求 Node.js 20.9 或更高版本。

```bash
npm install
cp .env.example .env.local
npm run dev            # http://localhost:3000
```

模型配置（`.env.local`，只在服务端读取，**不要**加 `NEXT_PUBLIC_` 前缀）：

```bash
AI_API_KEY=
AI_BASE_URL=https://api.openai.com/v1   # 任意 OpenAI 兼容端点
AI_MODEL=                               # 必须显式指定
```

三项留空即进入 Demo Mode。验证与容器：

```bash
npm run lint && npm run typecheck && npm run test && npm run build
docker compose up --build               # podman 用户：podman build --format docker -t atomforge .
```
